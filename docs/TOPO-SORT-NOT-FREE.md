## 但渲染崩了，而且崩得更彻底

```
ERR: PJe is not a constructor
```

**连测试页都跑不起来**（之前至少能拿到 98 个 OK）。

## 为什么

**拓扑排序只保证「声明依赖」的顺序，但没有考虑「模块级副作用」。**

举例（真实场景的简化）：

```js
// 原顺序（能工作）
var a = makeA();              // ← 有副作用：创建对象
function b() { return useA(); }
var result = b();             // ← 此时 a 已赋值 ✓

// 排序后（崩）
function b() { return useA(); }
var result = b();             // ← a 还没赋值 → undefined → 崩
var a = makeA();
```

**拓扑排序看到的是「b 引用 a」，所以把 a 排在 b 后面。**
但 `b` 的**调用点**（`var result = b()`）也在模块顶层，
它执行时 `a` 还没赋值。

**声明顺序对了，执行顺序错了。**

更麻烦的是 `var` 有 hoisting：`var a` 在两个位置都是 `undefined`，
不会报 TDZ，而是直接 `undefined` → 更难排查（`PJe is not a constructor`
就是拿了个 undefined 当构造器用）。

## 结论

**拓扑排序不是免费的。** 它解决不了这个问题，反而让错误更难理解。

**已回退** `gen-main.cjs`（`git checkout`），基线恢复。

## 正确的做法（如果要继续）

**必须同时考虑「声明顺序」和「副作用顺序」**：

1. **区分纯声明与有副作用的初始化**
   - `function f() {}` —— 纯声明，顺序无关（hoisting）
   - `var a = 1` —— 简单初始化，可重排
   - `var a = makeA()` —— 有副作用，**不能重排**

2. **对「有副作用的初始化」保留原相对顺序**
   只对纯声明（尤其是 `function`）和简单字面量初始化做拓扑排序

3. **或者换个思路：不排序，改成「延迟初始化」**
   把循环里涉及的符号改成：
   ```js
   let a;                      // 提前声明
   // ... 其他代码 ...
   a = makeA();                // 在原位置赋值
   ```
   这样 hoisting 有了、顺序也没变。

**第 3 条更安全**，因为它不改变任何语句的执行位置，
只是把「声明」和「赋值」分开——这正是 `var` 原来就有的语义。
