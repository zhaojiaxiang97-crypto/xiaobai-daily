# 重建崩溃的真因：TDZ 循环依赖（不是树构建的问题）

> round-0503
>
> 目标：把匿名节点映射问题解决，让重建能跑起来。
> 结果：匿名节点不是问题（只占 11%），但撞到了更根本的东西。

## 修正上轮的误判

上轮我说「232 个节点里 119 个是匿名」，那是按**树节点计数**算错了。

按**去重后的实例**统计（今日工作页）：
- 总节点 **224**
- 有名字 **199**（89%）
- 其中能对应到 `.vue` 的 **111**（50%）
- 匿名只有 **25 个**，而且只有 **2 种**：
  - 18 个是 lucide 图标（`(r, {slots, attrs}) => e(c, {...iconNode...})`）
  - 7 个是内部组件（`(e, {slots}) => c(ge, Me(e), t)`）

**所以匿名节点根本不是主要障碍。**

## 补齐缺失组件：三源加载

写了「三源加载」：
1. `.vue`（88 个）
2. `vendor/ui/*.js` 按 `__name` 索引（补上 `DialogRoot`、`PopperRoot` 等）
3. Vue 内置（`Teleport` 等）

**索引到 153 个组件**（比 88 多 65 个）。

## 但渲染崩了 —— 而且根因很意外

`THROW: Cannot read properties of null (reading 'nextSibling')`

加了「透明容器跳过」（`Presence`/`Teleport`/`BaseTransition` 等）也不行。
二分 depth=1 就崩 —— 说明问题在根级。

**于是单独测试每个组件：**

| 组件 | 结果 |
|---|---|
| 对照组（最简 `h('div','control-ok')`） | ✅ `<div>control-ok</div>` |
| **`App.vue`** | **`THROW: Cannot access 'G9' before initialization`** |
| **`Sidebar`** | **同样 THROW** |
| **`TodayWork`** | **同样 THROW** |
| `DialogRoot` | notfound（不在 .vue 里） |
| `DialogContent` | `OK:0`（渲染了但空） |

## 根因

**`Cannot access 'G9' before initialization` = TDZ 错误（暂时性死区）。**

这是**模块级循环依赖**：`shared.js` 里的某个符号在定义前就被引用了。

**这解释了之前「98/392 可渲染」的另一面** —— 那些渲染失败的组件里，
有一部分就是这个 TDZ 问题，而不是「需要 props 或父组件」。

### 为什么会出现

`shared.js` 是从 `main.js` 的 7548 个本地符号生成的，
这些符号之间原本在同一个模块作用域里，互相引用没问题。
但拆成 `shared.js` + 302 个跨 chunk import 后，
**如果 A 依赖 B、B 又依赖 A，ESM 的求值顺序就会触达 TDZ。**

## 修复方向（明确）

**需要让 `shared.js` 的符号定义按依赖顺序排列**：

1. 对 7548 个本地符号做**依赖图分析**（谁引用谁）
2. 拓扑排序，被依赖的先定义
3. 检测出真正的循环（无法拓扑排序的），用延迟初始化（`let` + 函数包装）打破

**这是改 `gen-main.cjs` 的符号生成逻辑** —— 中等工作量，
但能一次性修掉一批「莫名其妙渲染失败」的组件。

## 结论

| 项 | 状态 |
|---|---|
| 匿名节点映射 | ✅ 不是问题（只 11%，且是图标） |
| 三源加载补齐 | ✅ 索引到 153 个组件 |
| 树数据 | ✅ 224 节点 / 199 有名 / 111 可对应 |
| **重建渲染** | ❌ **卡在 TDZ 循环依赖** |
| **TDZ 根因** | ✅ **已定位（`G9`，模块级循环依赖）** |

**这轮最大的收获不是重建成功，而是定位到了 TDZ 这个一直存在的隐藏问题** ——
它同时解释了：
- 为什么有些组件「能 import 但渲染就崩」
- 为什么重建时根级就 THROW

## 下一步

按上面的修复方向做 `shared.js` 的拓扑排序。**这是可验证、可交付的**：
改完后重测 392 个组件的渲染率，如果能从 98 涨到更多，就证明修对了。
