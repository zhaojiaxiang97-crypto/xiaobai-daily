# 23 个 Vue API 映射的应用结果：几乎没有用武之地

> round-0491
>
> 上轮拿到 23 个确定性映射（`gt` = `openBlock` 等）。这轮试着应用，**发现收益极小**。

## 尝试

想把这 23 个映射应用到生成器，让 `.vue` 里的 `gt(true)` 变成 `openBlock(true)`。

## 结果：只影响 34 处

统计生成产物里这 23 个符号的出现次数：

| 符号 | Vue API | main 组件里出现 | vendor 组件里出现 |
|---|---|---|---|
| `g` | callWithErrorHandling | 14 | **0** |
| `b` | createBlock | 7 | **0** |
| `T` | createRenderer | 7 | **0** |
| `S` | createElementBlock | 3 | **0** |
| `gt` | openBlock | 2 | **0** |
| `rt` | nextTick | 1 | **0** |
| 其余 17 个 | — | 0 | 0 |
| **合计** | | **34** | **0** |

**392 个 main 组件 + 145 个 vendor 组件，总共只有 34 处能替换。**

## 为什么

**两条生成线早就做了这件事**：

- `gen-main.cjs` 的统计里写着 `Vue改写 554` —— 它已经把 Vue API 短名改写成语义名
- `lib-conv.cjs` 的 `apiOf()` 也做同样的翻译

**所以 `gt` 这类 runtime 导出名，在生成产物里基本不存在。**

## 那这 23 个映射还有什么价值

**不在于改善当前产物，而在于**：

1. **验证了方法**：归一化 AST 比对 + 1:1 交叉验证，能从压缩名确定性还原 API 名，
   可复现、可扩展
2. **纠正了一个错误判断**：round-0482 我手工分析 `runtime.On` = `unref`，
   实际是 `toValue`（`unref(x)` = `isRef(x)?x.value:x`，
   `toValue(x)` = `isFunction(x)?x():unref(x)`）
3. **解开了一个悬案**：round-0459 追 `FocusScope` 的 `Cannot destructure
   property 'slots'` 时卡在 `gt(true)`，现在确定它是 `openBlock(true)`
4. **方法可复用**：以后处理其他 Electron+Vue 应用，这套比对能直接用

## 真正的可读性瓶颈在哪

回顾 main.js 的短名分布统计：

| 排名 | 短名 | 次数 | 性质 |
|---|---|---|---|
| 1-7 | `e`/`t`/`n`/`r`/`i`/`a`/`o` | 合计 64,000+ | **局部变量/函数参数** |
| 8 | `H` | 3043 | 全局（= `withCtx`） |

前 25 个覆盖 **74.9%**，但**绝大多数是局部变量名** —— 压缩时语义已丢失，
**不可逆**。

**所以「进一步提升可读性」这条路的天花板就在这里**：
Vue API 名早就改好了（收益 34 处），剩下的 75% 是还原不了的局部变量。

## 结论

| 项 | 结果 |
|---|---|
| 23 个映射准确吗 | ✅ 是（1:1 交叉验证 + 一个独立印证） |
| 应用到当前产物有收益吗 | ❌ 只 34 处，不值得冒险改生成器 |
| 方法可复用吗 | ✅ 能 |
| 可读性还能提升吗 | ❌ 瓶颈在不可逆的局部变量名 |

**建议：不把这 23 个映射接进生成器。** 保留映射表和方法文档即可。
改动生成器的风险（七轮教训：任何改动都要对比基线 98）远大于 34 处替换的收益。
