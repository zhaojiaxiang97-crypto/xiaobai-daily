# 为什么 setup 内联必然让 OK 下降（第七轮，最终结论）

> round-0479

## 本轮尝试

把「内联全部 setup 顶层声明」改成「**只内联模板引用到的 + 依赖闭包**」
（这是 round-0458 最初的设计，round-0472 改成全部内联后才跑偏的）。

| 版本 | 内联范围 | OK | slots | `$setup` |
|---|---|---|---|---|
| 基线 | 不内联 | **98** | 59 | 11 |
| round-0472 | 全部 setup | 42 | 0 | 61 |
| round-0473/0478 | 全部 + 四条修法 | 44 | 0 | 60 |
| **0479** | **按需 + 依赖闭包 + 四修法** | **49** | **0** | **62** |

**按需内联好一点（44→49），但仍然比基线低 49 个。**

## 为什么必然下降

看 `AiModelSettings` 的 `i`（i18n 的 `t` 函数）：

### 基线版本

```js
import { S_i as i } from '../shared.js';
```

模板 `i('settings.xxx')` → **`S_i` 是一个函数**（哪怕是错的，也至少可调用或至少是某种值）。

### 内联版本

```js
const { t: i } = it();     // it = S_it = useI18n(gf)
```

模板 `i(...)` → **`it()` 返回的对象里没有 `t`** → `i` = undefined
→ `$setup.i is not a function`。

## 核心结论

**setup 内联把「一个能用的 shared 符号」换成了「一个不能用的内联解构」。**

- 基线里，模板引用的短名由 shared 补位。**这些符号有时是错的（如 `S_l` = Za），
  但也有时是对的（如 `S_i`、`S_it` = useI18n）**
- 内联后，短名改由 setup 内的表达式求值。而这些表达式**依赖运行时上下文**
  （i18n 插件、props、父组件），在测试环境下求值结果往往是 undefined

**所以内联不是「修 bug」，是「把静态可用的符号换成了动态不可用的值」。**

## 该彻底停止了

**不建议再做任何 setup 内联相关的改动。**

`gen-main.cjs` 维持基线（OK 98，已回退）。

## 唯一还可能有价值的两件事

1. **`slots` 那 59 个**：内联确实让它们归零了（真实修复），
   但代价是另外 60 个变成 `$setup` 错误。**净负。**
2. **`vendor chunk` 转换**：让 import 指向转换后的 `.vue` 而不是原始 `.js`。
   这条路和 setup 内联是**正交的**，理论上不会引入 `$setup` 问题。
   但需要映射表全覆盖（当前 107/644），成本高、收益未验证。

## 我的判断

**这条路（提升 main bundle 渲染率）的投入产出已经很差。**
七轮下来，基线 98 从未被超越。继续投入更可能是第八轮同样失败。

**如果还要做，应该换目标**：不是「提升渲染率」，而是
「提升组件可读性 / 可复用性」——比如把 `Za`、`gf` 这些符号还原成
`isInForm`、`useI18n` 这样的真名。那个方向不依赖运行时，是纯静态的，
成功率高得多。
