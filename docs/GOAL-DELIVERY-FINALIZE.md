# 目标确定：交付收尾（组件纳入仓库 + 可用性清单）

> round-0484（goal round 3）
>
> 前两轮定的目标是「符号还原」。这轮核实后发现**那条路的上限很低**，
> 转而发现了更实际的问题：**组件产物不在仓库里。**

## 为什么符号还原上限低

统计 `main.js` 里所有短名（≤2 字符）的引用频次：

| 排名 | 短名 | 次数 |
|---|---|---|
| 1-7 | `e` / `t` / `n` / `r` / `i` / `a` / `o` | 20718 / 13979 / 9321 / 7280 / 5662 / 4299 / 3665 |
| 8 | `H` | 3043 |
| … | … | … |

前 25 个覆盖 74.9%，前 100 个覆盖 85.1%。

**但 `e`/`t`/`n`/`r`/`i`/`a`/`o` 是局部变量和函数参数名** ——
压缩时语义信息**已经丢失，不可逆**。

唯一已知的全局符号是 `H` = `withCtx`（上轮确认）。

**所以「符号还原」能做的只有 `H` 这种极少数全局符号，
局部变量名没有还原的可能。**

## 真正的问题：组件不在仓库里

| 项 | 状态 |
|---|---|
| 应用源码（反混淆后） | ✅ 在仓库（50M） |
| `build.sh` 一键构建 | ✅ 可用 |
| **537 个生成的 `.vue`** | ❌ **只在 Release，仓库里只有 3 个样例** |
| 文档 | ✅ 27 份 |

**用户 clone 仓库后拿不到组件**，必须额外去 Release 下载 32MB 的包。

**这与最初的需求不符**：「拿到这个仓库中的源代码就可以直接编译出对应的离线版本」
—— 组件也是产出的一部分。

## 目标

**把 537 个生成的 `.vue` 纳入仓库，并附一份「可用性清单」。**

### 为什么可行

- 仓库当前 76M（源码 50M），组件包 32M
- `.vue` 是纯文本，git 会压缩存储，实际增长有限
- 用户 clone 就能拿到全部产物，不用再去 Release

### 为什么需要清单

**这些组件多数不能单独渲染**（main 109/392、vendor 10/145）。
如果直接放进去，用户会以为是「537 个能用的组件」，然后一个个试才发现多数不行。

**清单要说清楚**：
- 哪些能独立渲染（附已验证的结果）
- 哪些需要父组件上下文或真实 props
- 哪些只有结构、没有可用行为

## 具体做法

1. 把 Release 里的 `vue-components-v1.8.3.tar.gz` 解包内容放进仓库
   （`vue/main/` 392 个 + `vue/vendor/` 145 个）
2. 生成 `vue/README.md`：结构说明 + 可用性清单 + 使用方法
3. 跑一遍真实的渲染验证，把结果写进清单（不能凭印象）
4. 更新 `docs/DELIVERY.md` 的入口说明

## 与之前目标的关系

| 目标 | 状态 |
|---|---|
| 提升渲染率 | ❌ 七轮失败（98 是天花板） |
| 符号还原 | ⚠️ 上限低（只有全局符号可还原） |
| **交付收尾** | ✅ **本轮确定，可行性已核实** |

## 判断

**这是当前最该做的事。** 前面十几轮都在优化「质量」，但「可用性」还有个
明显的洞：**产物不在用户拿到的地方**。

修这个洞的成本很低（复制文件 + 写一份诚实的清单），
但它决定了用户拿到仓库后能不能直接用。
